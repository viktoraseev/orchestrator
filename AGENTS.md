# Правила разработки orchestrator

##
- This project uses a CLI ticket system for task management. Run `tk help` when you need to use it. It doesnt use yandex-tracker, do not load it.

## Источники требований

- При написании, ревью и рефакторинге Rust-кода используйте `$rust-skills` как единственный источник общих Rust-рекомендаций; не копируйте их сюда.
- `features/*.feature` содержат контракт config, source workflow и prompt templates, run, Agent attempts, read-only inspection и workflow graph, включая cycles, terminal и blocked run, planning и validation, `format.spec.md` — durable layout и форматы materialized run-файлов, а `cli.md` — публичный контракт команд, вывода, exit codes и сигналов. Изменение поведения требует одновременного обновления соответствующего документа и acceptance-сценариев.

## Границы проекта

- Пока проект остаётся одним crate: `orchestrator` — тонкий CLI-вход над библиотечной частью, которая содержит всю логику и публичный lifecycle API для Cucumber; бинарник только разбирает CLI, подключает process-зависимости и отображает результат API.
- Организуйте код вокруг сущностей из продуктовых спецификаций: run, workflow, step, agent, agent type, agent attempt, agent session activation и artifact. Не добавляйте слои и отдельные crates без новой независимой границы.
- Запуск агента и распознавание его исходов находятся только в адаптере соответствующего agent type. Остальной код не должен зависеть от деталей CLI или протокола Codex/Claude.
- Чтение, блокировка и атомарная публикация состояния run проходят через одну storage-границу. Нельзя оставлять состояние, которое `resume` не может однозначно восстановить.

## Тестовый контур

- Сквозные сценарии жизненного цикла описывайте в `features/*.feature`; основной режим Cucumber вызывает публичный lifecycle API библиотечной части и наблюдает его результат, durable-состояние и журнал in-memory fake agent, не создавая процессы.
- API driver вызывает тот же lifecycle entrypoint, что и CLI после разбора аргументов, и не обращается напрямую к scheduler, graph engine или storage; заменяются только process-зависимости на границе `AgentType` и представление результата, поэтому API-сценарий остаётся сквозной проверкой библиотечной логики.
- Сценарий помечается `@process` и запускает настоящий бинарник только когда проверяемый контракт нельзя наблюдать через lifecycle API: он зависит от CLI parsing, stdout/stderr, exit code, сигналов, TTY, process groups, времени жизни kernel lock, конкуренции отдельных процессов или построения и интерпретации реального agent process; наличие удобного process harness само по себе не является основанием выбирать этот режим.
- API- и process-режимы используют одни step definitions и одну модель наблюдаемых результатов; World выбирает driver по тегу сценария, по умолчанию использует API driver, а дублировать один сценарий в обоих режимах без отдельного наблюдаемого контракта не нужно.
- Шаги не содержат альтернативной реализации бизнес-логики: они готовят вход и сравнивают наблюдаемый результат с ожиданием, заданным в сценарии явно, но не вычисляют это ожидание сами.
- Детерминизм: API driver управляет fake agent через явные события без таймеров; process driver синхронизируется только опросом наблюдаемого состояния с дедлайном, `sleep` как средство синхронизации запрещён; корень состояния, временные пути и local endpoint уникальны на сценарий; процессы-сироты убиваются в teardown. Ожидание завершения агентов и control calls при graceful shutdown — не более 10 секунд по `cli.md` — не конфигурируется: инъекция короткого значения ради скорости подтверждала бы настраиваемый таймаут, а не константу из документа. Поэтому сценарий эскалации по истечении времени длится эти 10 секунд и помечается как `@process` и как медленный; эскалация по второму сигналу проверяется мгновенно.
- `features/*.feature` являются конечной исполняемой спецификацией продуктового поведения. В них должны находиться все наблюдаемые контракты: CLI, правила workflow и validation, переходы durable-состояния, scheduling, recovery, конкурентность, сигналы и границы Agent type. Ни одно такое правило не должно оставаться покрытым только unit-тестом, кроме исключения ниже.
- Покрытие задаётся правилом, а не списком в этом файле: каждое нормативное правило `format.spec.md` и `cli.md` обязано иметь минимум один подтверждающий сценарий. Непокрытое нормативное правило — дефект независимо от unit-покрытия. Перечень конкретных продуктовых сценариев ведётся только в feature-файлах: `AGENTS.md` не хранит его копию, иначе появляется третий текстовый источник истины, который придётся синхронно обновлять. При расхождении источником считается пара «документ-источник + feature».
- Единственное исключение из полного покрытия: правило, наблюдаемое только инъекцией сбоя внутрь процесса — crash в конкретной точке между временным файлом и публикацией. Его подтверждает unit-тест, а `@process` feature покрывает наблюдаемое снаружи следствие: восстановление до последнего подтверждённого durable-состояния после SIGKILL. Расширять исключение на другие правила нельзя: точка crash — не основной сценарий продукта, всё остальное наблюдаемо через API или бинарник.
- Трассировка: каждый `Rule`, которому соответствует раздел сохранившегося документа-источника, помечается тегом `@format:<anchor>` или `@cli:<anchor>`, где anchor — раздел соответствующего документа. Изменение раздела требует обновления всех сценариев с его тегом; перенесённый из удалённого документа контракт остаётся в `Rule` без source-тега.
- Новое или изменённое продуктовое поведение начинается со сценария: сначала правило в документе-источнике и `Rule` со сценарием, затем реализация. Ревью проверяет наличие тега источника и отсутствие правил без сценария, а не соответствие списку в `AGENTS.md`.
- Нормативное правило оформляйте как `Rule` и подтверждайте одним или несколькими сценариями либо `Scenario Outline`. Описательный текст `Feature` и `Rule` разрешён для терминов и контекста, но не заменяет исполняемый сценарий.
- Группируйте feature-файлы по возможностям и сущностям продукта, а не по модулям Rust или разделам временных документов. Шаги сценария описывают факты и наблюдаемый результат на языке продуктовых спецификаций, не вызовы функций и внутренний алгоритм.
- Unit-тесты проверяют локальную реализацию: чистые преобразования и парсеры, комбинаторные граничные случаи, agent-specific protocol parsing, внутренние инварианты storage и fault injection. Они могут расширять покрытие правила из feature, но не обязаны дублировать его основной acceptance-сценарий и не могут вводить новое продуктовое поведение.
- Test fixtures и Cucumber World могут создавать временные workflow, config, fake agent и намеренно повреждённое durable-состояние. Ожидаемый frontier, результат validation и восстановление они не вычисляют собственной реализацией: фактический результат берётся из lifecycle API в основном режиме либо из вывода бинарника в `@process`-режиме.
- Перед удалением `format.spec.md` и `cli.md` каждое их нормативное правило должно быть перенесено в `features/*.feature` и подтверждено сценарием. После удаления feature-файлы становятся единственным продуктовым контрактом; `AGENTS.md` продолжает содержать только правила разработки и тестового контура.
- В API-режиме World передаёт lifecycle API отдельный корень состояния и registry с in-memory fake `AgentType`; fake для всех type выполняет одинаковый управляемый сценарием протокол, идемпотентно записывает полученный prompt и ведёт журнал вызовов для наблюдения за scheduling, fan-out, выбором ветви и версиями artifacts.
- В `@process`-режиме изоляция задаётся переменными окружения, а не флагами: отдельный корень состояния и абсолютный путь единого fake agent executable в `ORC_AGENT_COMMAND`; поиск по `PATH` не выполняется, окружение наследуется дочерним `orchestrator`, поэтому настоящие Codex и Claude недостижимы, а доставка session ID и `attempt complete` остаётся в том же корне без явного проброса.
- Process fake agent различает вызвавший его Agent type по аргументам, но для каждого type ведёт себя одинаково и идемпотентно: записывает в output переданный prompt; это генерируемый фикстурой shell-скрипт с журналом вызовов, используемый только сценариями, которым необходима process-граница.
- Тесты не обращаются к корню состояния пользователя и сети.

## Стабильные команды

- `./scripts/test.sh` последовательно проверяет форматирование, запускает Clippy с предупреждениями как ошибками и весь детерминированный набор тестов, включая Cucumber test target.
- `./scripts/test-fast.sh` выполняет те же проверки, но исключает Cucumber-сценарии с тегом `@slow`; он предназначен для короткого локального цикла и не заменяет финальный `./scripts/test.sh`.
- `./scripts/test.sh` запускайте вне sandbox: `@process`-сценариям нужны Unix sockets, process groups и сигналы, а sandbox может вернуть `Operation not permitted` и каскадные timeout.
- `./scripts/test-fast.sh` также запускайте вне sandbox: исключение `@slow` не исключает остальные `@process`-сценарии.
- `./scripts/build.sh` собирает release-бинарь `orchestrator`.
- Перед завершением работы запускайте `./scripts/test.sh` и `./scripts/build.sh`; локальная разработка и CI используют эти команды как канонические проверки.

## Комментарии и Rustdoc

Rustdoc и внутренний комментарий решают разные задачи, поэтому правила для них различаются. Язык — русский.

| | Rustdoc (`//!`, `///`) | Внутренний (`//` в теле) |
|---|---|---|
| Отвечает на | контракт для вызывающего | причину решения |
| Длина | сколько нужно | одна строка |
| Начало строки | без timestamp | `// yyyy-MM-dd hh:mm` либо `// DEPRECATED yyyy-MM-dd hh:mm` |
| Живёт | пока жив элемент | пока жив функционал |
| Устаревшее | правится на месте | помечается, остаётся в журнале |

### Rustdoc

- Оформление — по `$rust-skills` (`doc-*`, `lint-missing-docs`), здесь не дублируется.
- Пиши только невыводимое из подписи и имён: точку durable-commit и что после неё видит `resume`, идемпотентность повтора, предусловия (удерживаемый lock, требуемый порядок вызовов), побочные эффекты вне возвращаемого значения (файлы, процессы, сигналы process group), смысл доменов (глобальная нумерация attempts, монотонность версий artifacts), условие каждой ошибки. Критерий отсева: содержание однозначно читается из типов — строка лишняя.
- Обязателен там, где такая семантика есть: публичный API библиотечной части (его вызывают Cucumber step definitions), storage-граница, scheduling, обработка сигналов, адаптеры Agent type. Чистые преобразования, парсеры и тривиальные конструкторы doc не требуют.
- `//!` у модуля: за какую границу он отвечает и чего в нём быть не должно.
- Ссылайся на реализуемый `Rule` в `features/*.feature`, а не на раздел `format.spec.md` или `cli.md`: feature-файлы остаются контрактом и после удаления этих документов. Связь `Rule` с документом-источником несёт его тег, поэтому при удалении документов правятся только теги, а не ссылки в коде.

### Внутренние комментарии

- Только «почему»: требования, предположения, ограничения, компромиссы, отвергнутые альтернативы и причины отказа от них. Пересказ кода не нужен.
- Для проверок и защитных ветвей — от какого сбоя или гонки они защищают; то же для параллельности, повторных вызовов и восстановления состояния. Сама защита из кода видна, её повод нет.
- Одна причина — одна строка без переноса, независимо от её длины: перенос разорвал бы запись журнала на строки без ts. Несколько причин — несколько строк, у каждой свой ts. Описание контракта, а не причины, переносится в Rustdoc.
- Не придумывай обоснований: неизвестное отмечай как вопрос или предположение.

### Устаревание

- Устаревшая причина остаётся в коде: журнал решений неполон, если из него вычищены отменённые причины. При пометке после `//` добавляется только `DEPRECATED`, а исходные timestamp и содержание строки сохраняются без изменений; timestamp момента пометки не добавляется. Если у функционала появилась новая актуальная причина, она записывается отдельным обычным комментарием со своим timestamp.
- Формат пометки: `// DEPRECATED yyyy-MM-dd hh:mm <original-content>`, где timestamp является исходным timestamp комментария. Помеченная строка не читается как текущее положение дел, поэтому неверных утверждений о поведении не возникает.
- Удаление строки — только вместе с функционалом, который она объясняет. При рефакторинге без изменения поведения журнал переезжает вместе с кодом.
- Rustdoc — исключение: он описывает текущий контракт, а не журнал, поэтому правится на месте вместе с поведением, а его история остаётся в VCS.
