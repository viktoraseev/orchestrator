# Правила разработки orchestrator

## Источники требований

- При написании, ревью и рефакторинге Rust-кода используйте `$rust-skills` как
  единственный источник общих Rust-рекомендаций; не копируйте их сюда.
- `SPEC.md` содержит контракт run и Agent attempts, `workflow.spec.md` —
  workflow graph и validation, а `cli.md` — публичный контракт команд, вывода,
  exit codes и сигналов. Изменение поведения требует одновременного обновления
  соответствующего документа и acceptance-сценариев.
- `idea.md` описывает более раннюю модель и не является требованием, пока её
  решения явно не перенесены в `SPEC.md`.

## Границы проекта

- Пока проект остаётся одним crate: `orchestrator` — тонкий CLI-вход, а
  тестируемая логика доступна через библиотечную часть crate.
- Организуйте код вокруг сущностей из `SPEC.md` и `workflow.spec.md`: run,
  workflow, step, agent type, agent attempt, agent session activation и artifact.
  Не добавляйте слои и отдельные crates без новой независимой границы.
- Запуск агента и распознавание его исходов находятся только в адаптере
  соответствующего agent type. Остальной код не должен зависеть от деталей
  CLI или протокола Codex/Claude.
- Чтение, блокировка и атомарная публикация состояния run проходят через
  одну storage-границу. Нельзя оставлять состояние, которое `resume` не может
  однозначно восстановить.

## Тестовый контур

- Сквозные сценарии жизненного цикла описывайте в `features/*.feature`.
  Cucumber step definitions вызывают библиотечный API и не содержат
  альтернативной реализации бизнес-логики.
- `features/*.feature` являются конечной исполняемой спецификацией продуктового
  поведения. В них должны находиться все наблюдаемые контракты: CLI, правила
  workflow и validation, переходы durable-состояния, scheduling, recovery,
  конкурентность, сигналы и границы Agent type. Ни одно такое правило не должно
  оставаться покрытым только unit-тестом.
- Нормативное правило оформляйте как `Rule` и подтверждайте одним или несколькими
  сценариями либо `Scenario Outline`. Описательный текст `Feature` и `Rule`
  разрешён для терминов и контекста, но не заменяет исполняемый сценарий.
- Группируйте feature-файлы по возможностям и сущностям продукта, а не по
  модулям Rust или разделам временных документов. Шаги сценария описывают факты
  и наблюдаемый результат на языке `SPEC.md`, не вызовы функций и внутренний
  алгоритм.
- Unit-тесты проверяют локальную реализацию: чистые преобразования и парсеры,
  комбинаторные граничные случаи, agent-specific protocol parsing, внутренние
  инварианты storage и fault injection. Они могут расширять покрытие правила из
  feature, но не обязаны дублировать его основной acceptance-сценарий и не могут
  вводить новое продуктовое поведение.
- Test fixtures и Cucumber World могут создавать временные workflow, config и
  намеренно повреждённое durable-состояние. Они не вычисляют ожидаемый frontier,
  результат validation или восстановление собственной реализацией: эти
  результаты получают только через библиотечный API orchestrator.
- Перед удалением `SPEC.md`, `workflow.spec.md` и `cli.md` каждое их нормативное
  правило должно быть перенесено в `features/*.feature` и подтверждено сценарием.
  После удаления feature-файлы становятся единственным продуктовым контрактом;
  `AGENTS.md` продолжает содержать только правила разработки и тестового контура.
- Тесты используют временный state directory и детерминированные fake agent
  adapters. Они не обращаются к настоящему `~/.orc`, сети, Codex или Claude.
- Обязательные acceptance-сценарии: start/resume, конкурентный resume одного
  run, два конкурентных start с одинаковым timestamp создают разные runs,
  существующий run не переиспользуется новым start независимо от `active.lock`,
  приоритет явного WorkflowId для start и validate, выбор `default-workflow` из
  `~/.orc/config.yaml`, автоматический выбор единственного workflow, отказ с
  отсортированным списком при неоднозначном выборе, отказ для отсутствующего
  default без fallback, `config get` для заданного и unset default,
  детерминированный `config list`, атомарный `config set` существующего workflow,
  отказ config-команд для неизвестного key, невалидного config и отсутствующего
  workflow без изменения файла, last durable commit для конкурентных config set,
  lookup workflow только в `~/.orc/workflow` и prompt templates только в
  `~/.orc/prompt` без cwd fallback,
  строгие kebab-case IDs без начального, конечного или повторного дефиса,
  вывод выбранного workflow, публикация и flush RunId после durable initial state
  и до запуска агента,
  стабильный lifecycle output и разделение stdout/stderr, exit codes `0`–`5`,
  `129`, `130` и `143`, resume неизвестного, завершённого, занятого и
  повреждённого run, blocked run с перечнем отсутствующих join requirements,
  глобальная нумерация attempts разных steps внутри run, явный `/exit`, ошибка
  агента, обязательный RunId и отсутствие implicit resume, отсутствие
  автоматического resume после выхода процесса, выбор последней Agent session
  activation в общем durable-порядке, единая команда `session activate` только
  с native session ID для create, resume и fork, выбор более поздней activation
  после fork, новая session при отсутствии activation,
  отказ validate для Agent type без native resume, fail-fast без вопросов при

  с возможностью последующего явного resume, восстановление незавершённого шага,

  fail-fast без запуска агента и изменения run для битого attempt record или

  initial activation первого описанного step с пустым input и `n = 0` при

## Стабильные команды

- `./scripts/test.sh` последовательно запускает Clippy с предупреждениями как
  ошибками и весь детерминированный набор тестов, включая Cucumber test target.
  Проверка форматирования в эту команду не входит.
- `./scripts/build.sh` собирает release-бинарь `orchestrator`.
- Локальная разработка и CI используют эти два скрипта как канонические
  однострочные команды проверки и сборки.

## Код, пояснения и комментарии
- Все комментарии в коде, пиши на русском языке.
- Объясняй не что делает код, а ТОЛЬКО почему реализован именно так: требования, предположения, ограничения, компромиссы и причины выбора подхода. Если комментарий состоит из обьяснений что делает код, или как он работает, он не нужен.
- Каждый комментарий выполняй одной строчкой, без переносов строки и предваряй ts добавления в формате `yyyy-MM-dd hh:mm`, формируя историю изменений.
- Удаляй комментарии только при удалении функционала.
- Документируй назначение модулей, типов и функций, включая внутренние. Для нетривиальных функций описывай входы, результат, побочные эффекты, ошибки и условия корректного вызова.
- Явно поясняй работу с параллельностью, зависимостями, повторными вызовами, сохранением и восстановлением состояния. Объясняй, от каких сбоев и гонок защищает конкретная проверка.
- Фиксируй причины неочевидных решений и обходных путей. Если известны отвергнутые альтернативы, объясняй, почему они не подошли. Не придумывай обоснования: неизвестное отмечай как вопрос или предположение.
