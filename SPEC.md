# Orchestrator: целевая спецификация

## Назначение

`orchestrator` — CLI для выполнения длинных задач агентами по заранее заданному
workflow. Выполнение сохраняется как run: его можно безопасно прервать,
продолжить в другом процессе и восстановить без контекста предыдущего запуска.
Публичные команды, вывод, коды завершения и обработка сигналов определены в
`cli.md`. Workflow graph, его validation и scheduling определены в
`workflow.spec.md`. Layout состояния, имена и содержимое файлов определены в
`format.spec.md`.

## Сущности

- **Run** — один сохраняемый запуск workflow. Идентификатор равен Unix
  timestamp создания в миллисекундах. Сам timestamp не считается гарантированно
  уникальным: уникальность обеспечивает атомарное резервирование каталога run.
  Run хранит материализованный workflow, записи фактов agent attempts и
  опубликованные артефакты по `format.spec.md`. Текущая позиция и состояние run
  отдельно не сохраняются: они вычисляются из этой модели.
- **Agent type** — встроенная реализация интерфейса `AgentType`; это не запись
  config. Текущий registry binary содержит type IDs `codex` и `claude`. Каждая
  реализация проверяет совместимость Agent с type, строит command и environment
  запуска из materialized Agent, input mapping, prompt и control context,
  выполняет native resume и интерпретирует протокол и завершение процесса. Путь исполняемого
  файла type переопределяется только переменной окружения из `cli.md`; это не
  меняет ни построение аргументов и environment запуска, ни интерпретацию
  протокола. Новый type появляется только с новой реализацией
  `AgentType`, зарегистрированной в binary. Type существует, если он есть в этом
  registry; type валиден, если его реализация принимает Agent и поддерживает
  native resume. Для одного и того же materialized workflow и валидного Agent
  attempt record он всегда детерминированно выводит один и тот же результат:
  успешное завершение шага либо необходимость продолжения attempt. Неизвестные или противоречивые
  agent-specific факты являются ошибкой. Успешное завершение требует
  положительного completion event, который агент отправляет вместе со всеми
  artifacts одним обычным tool call `orchestrator` и который публикуется в
  Agent attempt record; завершение процесса само по себе успехом не является. В
  human-режиме агент работает напрямую с терминалом; orchestrator не проксирует
  его stdin через PTY. В non-human режиме Agent type запускает агента без
  интерактивного терминала.
- **Agent** — именованная конфигурация агента формата `format.spec.md`.
  Допустимость параметров определяет выбранный Agent type. Agent выбирается Step
  или `default-agent` и materialize’ится вместе с workflow до создания run.
  Поэтому последующее изменение config не меняет Agent существующего run или
  его resume.
- **Agent attempt** — одна обработка конкретной Step activation. Её могут
  последовательно обрабатывать несколько процессов агента, в том числе через
  native resume. Attempt получает порядковый номер `n` из единой для всего run
  последовательности attempts всех steps и создаётся атомарной публикацией
  Agent attempt record формата `format.spec.md`. Полный набор выбранных входных
  номеров фиксируется первой публикацией и больше не изменяется. После каждого
  recovery-critical события главный процесс целиком атомарно заменяет запись;
  in-place изменений нет. Её содержимого вместе с materialized workflow
  достаточно, чтобы Agent type вывел результат attempt. Производные статусы вроде `running`, `paused` или
  `completed` не сохраняются. Продолжение незавершённого attempt использует тот
  же `n`; этот номер никогда не назначается другому attempt.
- **Agent session activation** — сообщение об активации внутренней сессии агента
  с её native session ID. Создание, продолжение и fork имеют одну семантику и не
  сохраняются как разные виды событий; при fork активируется дочерняя сессия.
  Agent type получает activation напрямую из протокола запущенного процесса,
  если это возможно. Agent-specific hook используется только когда native
  session ID иначе недоступен: он запускает
  дочерний процесс `orchestrator`, который передаёт событие parent supervisor по
  control endpoint. Активация не создаёт новый orchestrator Run.
- **Agent session view** — volatile-представление активной внутренней сессии
  агента для non-human attempt: количество полученных сообщений и последнее
  сообщение, нормализованное в одну строку. Agent type получает сообщения из
  output или event stream запущенного процесса. Они не записываются в Agent
  attempt record, поскольку не участвуют в recovery или вычислении готовности
  steps.
- **Artifact** — версионируемый сформированный результат с durable-ключом
  `(attempt-n, step-id, input-id)`. Правила его использования графом заданы в
  `workflow.spec.md`, а файловый формат — в `format.spec.md`. Artifact входит в
  durable-модель только вместе с completion event создавшего его attempt и с
  этого момента доступен графу и неизменяем.
- **Run lock** — эксклюзивная блокировка одного run. Пока её удерживает процесс
  `orchestrator`, второй процесс не может запустить тот же run; разные runs
  могут выполняться одновременно. Блокировка ядра берётся на lock-файле из
  `format.spec.md`; наличие файла само по себе не означает активность.

## Идентификаторы

- `RunId` основан на Unix timestamp создания в миллисекундах. Он уникален среди
  существующих runs благодаря атомарному созданию каталога, а не благодаря
  точности системных часов. Его файловое представление задано в
  `format.spec.md`.
- Порядковый номер Agent attempt — числовой счётчик, а не символический ID. Это
  единая глобальная последовательность внутри run, начиная с `0`; отдельных
  последовательностей для steps нет.

## Native resume

Продолжение run выполняется только явно с обязательным RunId; implicit resume
последнего run не поддерживается. Точный CLI-контракт задан в `cli.md`. После
выхода процесса без completion event orchestrator не запускает тот же attempt
повторно в рамках текущей команды.

При явном resume незавершённый attempt продолжает ту же внутреннюю сессию,
которая указана последней Agent session activation в durable-порядке
Agent attempt record. Причина её появления — create, resume или fork — не
сохраняется и не даёт ей отдельного приоритета. Если activations нет, Agent type
создаёт новую внутреннюю сессию для того же attempt и того же `n`.

Fallback с native resume на новую сессию запрещён. Agent type без поддержки
native resume отклоняется при `validate` и `start`; если такая несовместимость
обнаружена при `resume` существующего run, команда завершается fail-fast до
запуска агента и без интерактивных вопросов.

Ненулевой exit code процесса атомарно записывается как факт в Agent attempt
record и fail-fast завершает текущую команду: новые attempts и автоматический
native resume не запускаются. Наличие completion event определяет состояние
attempt независимо от exit code: с уже опубликованным event attempt завершён,
без него остаётся незавершённым и может быть продолжен только последующим явным
`orchestrator resume <run-id>`.

## Control endpoint и события

Supervisor, удерживающий Run lock, создаёт один volatile Unix domain socket
для всех дочерних процессов `orchestrator` данного run. Socket доступен только
владельцу каталога run и существует только во время работы supervisor; он не
является частью durable-модели. Один listener обслуживает краткоживущие запросы,
отдельные постоянные файловые дескрипторы для attempts или activations не
удерживаются.

Перед каждым запуском процесса агента supervisor передаёт через environment
endpoint, RunId и номер attempt. Дочерний `orchestrator`, вызванный hook или
обычным tool call, берёт этот контекст из environment; переданные самим агентом
RunId или номер attempt не считаются доверенными. В payload `session activate`
он передаёт native session ID. В payload `attempt complete` он передаёт
completion и список пар из `input-id` и пути к временному файлу. Точный
синтаксис обеих команд определён в `cli.md`.

Новое событие parent принимает только если контекст указывает на обслуживаемый
run и существующий attempt, который сейчас обрабатывается процессом агента под
управлением этого supervisor. Completion обрабатывается по правилам
идемпотентности независимо от состояния процесса.
Права Unix socket защищают endpoint от других локальных пользователей. Защита
от процесса, уже выполняющегося с теми же правами пользователя, не входит в
текущий scope.

Новая session activation сравнивается только с последней durable session
activation данного attempt. Если native session ID совпадает, запрос возвращает
прежний успех без изменения Agent attempt record; иначе ID добавляется в конец
списка.
Поэтому последовательность `a → b → a → a` сохраняется как `a → b → a`.
Повтор ID после другого ID является новой activation: порядок `a → b → a`
сохраняет выбор `a` для следующего native resume. Вид появления session — create,
resume или fork — на это правило не влияет. Отдельный идентификатор события не
создаётся. Completion в attempt может быть только один и повторяется по правилам
идемпотентности `attempt complete`.

Parent сериализует новые принятые события и наблюдаемые завершения процессов,
добавляя их в упорядоченный список фактов в Agent attempt record в порядке
durable commit. Позиция в списке определяет «последнюю» Agent session activation.
Parent сначала атомарно заменяет record, затем обновляет in-memory состояние и
только после этого отвечает дочернему процессу успехом. После crash in-memory
состояние восстанавливается из того же списка.

Запрос, принятый до фиксации завершения процесса, обрабатывается в общей очереди
раньше факта exit. После фиксации exit новые события от завершившегося процесса
отклоняются, а точный повтор того же `attempt complete` возвращает прежний
успех. После completion event новые session activations также отклоняются; точный
повтор того же `attempt complete` остаётся идемпотентным.

Если endpoint недоступен, control context невалиден или parent завершился,
дочерний `orchestrator` возвращает ненулевой exit code и не пишет файлы run
напрямую. Без успешного ответа caller не может определить, достиг ли запрос
commit-точки. `attempt complete` можно безопасно повторить: уже опубликованный
точный дубликат вернёт прежний успех, а не опубликованный запрос будет выполнен
впервые. Для `session activate` retry не является частью контракта.

После crash новый supervisor сначала получает Run lock, удаляет оставшийся
volatile socket path и создаёт endpoint с новым, не переиспользуемым путём.
Поэтому дочерние процессы со старым endpoint не могут отправлять события после
resume.

## Публикация artifacts и completion

Успешно закончив работу, агент формирует каждый artifact в отдельном уникальном
файле внутри временного каталога и одним tool call `orchestrator attempt
complete` передаёт по одной паре из `input-id` и пути для каждого объявленного
output текущего Step. При пустом `outputs` передаётся ноль artifacts. Имя
временного файла не участвует в durable-ключе и не ограничивается именами других
attempts. Временные файлы не входят в durable-модель run и должны сохраняться
caller'ом до успешного ответа.

Дочерний `orchestrator` берёт RunId и номер attempt из control context и
передаёт один запрос parent supervisor. Он не создаёт и не изменяет файлы
внутри каталога run. Parent до изменения run проверяет весь запрос: InputIds
из запроса совпадают с объявленными InputIds без пропусков и дополнений, а каждый
source является обычным файлом во временном каталоге. Затем parent полностью
читает их как непрозрачные bytes, публикует весь набор под durable-именами и
последним атомарно добавляет completion event в Agent attempt record. Только эта
последняя запись является commit-точкой всей операции и делает artifacts частью
durable-модели и графа. Перед commit физический набор файлов данного attempt
приводится ровно к набору из текущего запроса: остатки предыдущего
незавершённого вызова не могут случайно войти в результат.

Crash до commit-точки может оставить файлы под durable-именами, но без
completion они не являются artifacts модели и при восстановлении игнорируются.
Повторный `attempt complete` может заменить такие остатки. После commit набор и
содержимое artifacts неизменяемы. Точный повтор с теми же InputIds и
побайтово равным содержимым возвращает прежний успех; любой другой повтор
отклоняется без изменения run.

Parent supervisor является единственным поддерживаемым писателем artifact-файлов
внутри run. Прямая запись агентом или другим процессом нарушает storage-контракт;
защита и обнаружение изменений со стороны процесса того же локального
пользователя не входят в текущий scope.

## Блокировка run

Перед запуском первого шага через `start` или `resume` процесс открывает lock-файл
выбранного run и неблокирующе получает exclusive kernel lock.
Занятый lock завершает команду с ошибкой до запуска агента.

При `start` процесс получает timestamp-кандидат и атомарно резервирует каталог
run из layout `format.spec.md` только при отсутствии такого каталога. Победитель
сразу получает RunId. Если каталог уже существует, кандидат не переиспользуется:
`start` дожидается другого значения timestamp и повторяет атомарное
резервирование. Существующий каталог никогда не присоединяется к новому `start`.
Ошибка резервирования, отличная от коллизии имени, завершает `start`.

После успешного резервирования новый run захватывает собственный Run lock
по общим правилам выполнения. Этот lock не участвует в выборе RunId и нужен
только для запрета одновременного выполнения уже созданного run.

Любой шаг разрешено запускать только supervisor, уже удерживающему
Run lock. Между последовательными запусками steps lock не освобождается и
повторно не захватывается. Поэтому весь непрерывный проход по workflow защищён
одной блокировкой.

Ядро освобождает Run lock при штатном выходе, crash или завершении
процесса. GC и другие операции перемещения или удаления run не входят в
текущий scope.

## Создание и восстановление Agent attempt

Атомарная публикация Agent attempt record является единственной commit-точкой
создания Agent attempt. До неё attempt не существует. Следующий
новый attempt любого step получает `0`, если во всём run ещё нет опубликованных
attempt records, иначе на единицу больше максимального использованного во всём
run `n`; пропуски не заполняются. Так artifact, оставшийся после crash до
создания attempt, не вызывает повторного использования своего имени.

Отдельной commit-точки в виде `output` нет. После получения Run lock
orchestrator читает факты из каждого Agent attempt record, а соответствующий
Agent type выводит из них и materialized workflow, завершён ли attempt успешно
или требует продолжения:

| Durable-состояние | Значение | Действие при `resume` |
| --- | --- | --- |
| Agent attempt record отсутствует | Attempt не существует. Оставшиеся artifacts или временные файлы сами по себе его не создают. | Не восстанавливать attempt; такие файлы не участвуют в workflow. |
| Completion event отсутствует, как и подтверждённая Agent session activation | Attempt создан, но запуск внутренней сессии не подтверждён durable. | Продолжить тот же attempt с тем же `n`, запустив новую внутреннюю сессию агента. |
| Completion event отсутствует, но есть activations, завершения процессов или оставшиеся после прерванного completion файлы | Attempt не завершён. В частности, `/exit`, crash и обычное завершение процесса сами по себе не завершают шаг. | Только по явному `resume` продолжить последнюю activation в общем durable-порядке. Незавершённые файлы не передаются агенту и не участвуют в графе. |
| Последний процесс завершился с ненулевым code без completion event | Attempt не завершён, а предыдущая команда окончилась fail-fast. | Не продолжать автоматически; последующий явный `resume` продолжает последнюю durable activation. |
| Валидный completion event опубликован и присутствуют все объявленные artifacts | Attempt успешно завершён; его artifacts зафиксированы. При пустом `outputs` их нет. | Не запускать агент; сделать artifacts доступными и пересчитать graph по `workflow.spec.md`. |
| Agent attempt record или artifact завершённого attempt не соответствует `format.spec.md` либо durable input activation противоречит `workflow.spec.md` | Run невозможно однозначно восстановить. | Завершить `resume` с ошибкой до запуска агента. |

Artifacts и completion публикуются только одной операцией `attempt complete`.
После успешного ответа её набор и содержимое зафиксированы. Crash или `/exit` до
commit-точки оставляет attempt незавершённым, а возможные файловые остатки не
сохраняют частичный результат агента и не участвуют в восстановлении.

Artifact без соответствующего Agent attempt record, файловый остаток attempt без
completion и временный файл атомарной записи не входят в модель и игнорируются;
их автоматическая очистка не входит в текущий scope.

## Fail-fast восстановление

После получения Run lock, но до запуска агента, вычисления frontier
или любой durable-записи orchestrator полностью проверяет materialized workflow,
все Agent attempt records и artifacts успешно завершённых attempts. Все файлы
должны соответствовать `format.spec.md` и не противоречить остальным фактам run;
соответствие workflow graph и durable input activation проверяется по
`workflow.spec.md`.

Любая ошибка этой проверки завершает `start` или `resume` до запуска агентов и
без изменения durable-модели run. Временные файлы атомарной записи, artifacts
без соответствующего attempt и файловые остатки attempt без completion моделью
не являются и на результат проверки не влияют.

После успешной проверки результат каждого attempt вычисляется только его Agent
type из materialized workflow и полного содержимого Agent attempt record;
отдельный сохранённый status не используется.

## Главный workflow

1. `orchestrator start` получает выбранный workflow, применяет те же проверки,
   что `validate`, и материализует его до создания каких-либо данных run.
2. CLI резервирует свободный RunId по правилам разрешения timestamp-коллизий,
   создаёт каталог run и входит в выполнение, захватив exclusive Run lock.
3. `start` и последующие scheduling passes создают Agent attempts только по
   правилам initial activation, dependencies, нумерации и durable inputs из
   `workflow.spec.md`; публикация attempt навсегда фиксирует его input.
4. Выбранные source attempts образуют input mapping, где artifact адресуется
   ключом `(source-step-id, input-id)`. Из необязательного Markdown template
   формируется prompt: placeholders заменяются путями или содержимым artifacts
   по `format.spec.md`. Supervisor передаёт Agent type input mapping, prompt и
   control context, после чего тот запускает агента или выполняет native resume.
   Native session ID активированной сессии берётся из протокола процесса либо,
   только если иначе нельзя, из agent-specific hook. Message events для
   non-human view Agent type читает из output или event stream процесса.
5. Пока attempt не завершён, сформированные агентом временные файлы не входят в
   модель run. Crash до финального tool call может потребовать сформировать их
   заново; промежуточной durable-публикации черновиков нет.
6. Успешно закончив работу, агент одним tool call `orchestrator attempt complete`
   передаёт все artifacts и completion. Orchestrator проверяет весь запрос,
   публикует artifacts и последним атомарно добавляет event в Agent attempt record;
   tool call возвращает успех только после durable commit.
   С этого момента artifacts неизменяемы, а graph пересчитывается по
   `workflow.spec.md`. Completion принимается только с точным набором artifacts,
   объявленным в `outputs` Step.
7. Если completion event не опубликован, attempt остаётся незавершённым.
   Пользовательский `/exit`, crash и завершение процесса не меняют этого правила,
   даже если агент уже создал временные файлы. Завершение процесса supervisor
   наблюдает напрямую и атомарно добавляет как факт в Agent attempt record; hook для
   этого не используется. После durable exit fact новые события завершившегося
   процесса отклоняются. Любой ненулевой exit code fail-fast завершает текущую
   команду независимо от наличия completion event, а при любом exit без event
   автоматический перезапуск того же attempt не выполняется. При создании
   следующих activations Run lock остаётся у того же supervisor; при
   завершении процесса lock освобождается ядром. Производные статусы run или
   attempt на диск не записываются.
8. `orchestrator resume <run-id>` захватывает Run lock, находит
   и проверяет полную durable-модель run по fail-fast правилам. Только после
   успешной проверки он находит незавершённые attempts и вычисляет ready
   activations по правилам `workflow.spec.md`. Незавершённые attempts и новые
   activations запускаются по scheduling rules того же документа. Для каждого
   незавершённого attempt используется
   его последняя durable Agent session activation; при её отсутствии создаётся
   новая внутренняя сессия. Занятый lock завершает команду с ошибкой до запуска
   агентов.
9. `resume` применяет таблицу восстановления ко всем опубликованным Agent
   attempt records; отдельная state-запись и обязательный output-маркер для этого
   не нужны.
