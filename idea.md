# Решения о поведении harness

Этот файл фиксирует принятые решения о поведении launcher, orchestrator и
workflow подготовки worktree. Реализация остаётся источником истины для
технических деталей.

## Используемые понятия

- **Harness** — персональный набор rules, skills и agents для работы Codex в
  `adv/promopages`.
- **Preset** — декларация состава harness, которую launcher передаёт AISuite.
- **Launcher** — точка установки harness в Arcadia checkout.
- **Workflow** — сценарий подготовки worktree и переключения активного run в
  него.
- **Orchestrator** — процесс, который создаёт и продолжает runs, запускает
  Codex в сохранённой рабочей папке и обрабатывает сообщения workflow.
- **Run** — сохраняемый контекст работы orchestrator, который может пережить
  завершение процесса Codex и продолжиться в другой рабочей папке.
- **Run state** — сохранённый абсолютный путь рабочей папки run.
- **Run lock** — удерживаемая ядром эксклюзивная блокировка конкретного run,
  не позволяющая двум orchestrator processes одновременно продолжать один
  `run_id`.
- **Working directory** — каталог Arcadia checkout, в котором orchestrator
  запускает или продолжает Codex.
- **Session** — сессия Codex, которую можно продолжить внутри run.
- **Session activation** — зафиксированный момент появления сессии в run.
  Последняя активация определяет сессию для продолжения.
- **Worktree** — отдельный Arc checkout, подготовленный workflow для работы
  над задачей.
- **Action** — отдельный последовательный шаг workflow с собственной границей
  ошибки.
- **Message** — атомарно записываемая команда от workflow к orchestrator;
  протокол поддерживает команду `restart-agent`.
- **Git indicator** — пустой Git-репозиторий строго в корне Arc worktree,
  используемый только для отображения короткого имени задачи в statusline
  Codex.
- **Main Arc mount** — основной checkout, который хранится в конфигурации
  orchestrator и используется для обновления trunk.
- **Project override** — набор персональных project instructions, который
  хранится в harness вне целевого проекта и применяется к соответствующему
  Arc checkout.

## Launcher

Launcher собирает только явно указанный персональный preset и записывает
сгенерированную конфигурацию в `adv/promopages`. Корень checkout вычисляется
относительно расположения launcher, поэтому один и тот же механизм работает в
основном checkout и arc-wt worktrees.

Основная инструкция skill содержит частый рабочий путь. Редкие операции могут
быть вынесены в соседнюю extended-инструкцию, которая читается только для
соответствующей задачи.

## Arc CLI

Все команды `arc`, включая read-only проверки состояния и ветки, workflow
запускает вне sandbox с первой попытки. Пробный запуск в sandbox не делается:
доступ к Arc mount process из sandbox не гарантирован.

Для просмотра состояния checkout и связанного run workflow вызывает `orc info`,
также вне sandbox с первой попытки: `orc` внутри обращается к Arc mount process.

## Persistent runs

Перед каждым фактическим запуском Codex orchestrator выполняет единый
pre-launch pipeline. Он проверяет executable Codex, читает и валидирует
конфигурацию main Arc mount, проверяет рабочую папку и её Arc checkout,
проверяет обязательный системный prompt, обновляет ссылку trunk в текущем
checkout, обеспечивает наличие Git indicator и устанавливает project
overrides. При отсутствии конфигурации выбирается смонтированный checkout с
наибольшим доступным store, после чего результат атомарно сохраняется. Ошибка
любого шага pipeline завершает run до запуска Codex.

Новый run получает числовой идентификатор на основе текущего времени и
сохраняет текущую рабочую папку. Run state содержит только этот абсолютный путь
одной строкой. Идентификаторы сессий хранятся отдельно в неизменяемой истории
session activations.

Перед записью состояния нового run orchestrator захватывает его run lock.
Перед чтением session activation при resume существующего run orchestrator
также захватывает lock и при занятой блокировке завершается без запуска Codex.
Lock удерживается одним supervisor на протяжении всех запусков и restart этого
run. Блокировка относится только к конкретному `run_id`: разные runs могут
работать одновременно, а read-only команды `info`, `list` и `cd` её не
захватывают.

Run lock реализован через файловую блокировку ядра. Файл `active.lock`
сохраняется в каталоге run, но его наличие не считается признаком активности.
После завершения процесса, аварии или reset компьютера ядро освобождает
блокировку; следующий resume захватывает тот же файл.

## Garbage collection runs и worktrees

`orc gc` сразу переносит подходящие run directories из `runs/` в
`trash/runs/`. По умолчанию runs не защищаются по количеству (`keep-last=0`),
а retention threshold равен 3 дням. Параметры `--keep-last <count>` и
`--retention <duration>` переопределяют эти значения; duration принимает `0`
или целое число с единицей `s`, `m`, `h`, `d`, `w`. `--dry-run` только
показывает решение без создания недостающих run lock-файлов и перемещения
runs. `--verbose` выводит действие или конкретную причину сохранения для
каждого проверенного saved run, trashed run и Arc worktree по мере обработки;
без этого флага вывод остаётся компактным и не показывает штатные `KEPT`,
`EXCLUDED` и большинство диагностических `CHECK`.

В интерактивном терминале оба режима используют общую цветовую легенду:

- зелёные `REMOVED`, `COLLECTED`, `DELETED` и `PURGED` означают завершённое
  удаление или перенос;
- голубые `WOULD REMOVE`, `WOULD COLLECT` и `WOULD DELETE` показывают действие,
  которое выполнил бы `--dry-run`;
- жёлтый `IN USE` означает временную защиту: worktree является текущим,
  связан с сохранённым run или его mount удерживает процесс. Такой worktree
  можно будет проверить снова после завершения работы;
- красный `NEEDS ATTENTION` означает, что checkout dirty или его HEAD ещё не
  находится в remote trunk. GC сам такой worktree не удалит;
- тусклые `CHECK`, `KEPT` и `EXCLUDED` являются контекстом, а не проблемой.

`NO_COLOR` полностью отключает ANSI. Итог выводится отдельными строками для
runs, trash и worktrees. В dry-run поле `would remove` означает число
worktrees, которые были бы переданы на удаление. В настоящем GC показываются
фактически `removed`, временно `in use` и требующие вмешательства
`needs attention`. Старое поле `worktree-candidates` означало количество
worktrees, признанных безопасными для попытки удаления, включая mount, который
мог оказаться busy только во время unmount. Из пользовательского вывода это
неоднозначное поле удалено.

Активность run определяется как максимум времени создания из `run_id`, всех
session activation timestamps и времени последнего user/agent message во всех
связанных текущих Codex session JSONL из `~/.codex/sessions`. Отсутствующий
session log не делает run невалидным: для него учитывается activation
timestamp. `~/.codex/archived_sessions` orchestrator не читает и не очищает;
archived session считается не найденной. Run становится
кандидатом, только если он не входит в keep-last и его активность старше
retention threshold. Затем GC пропускает pinned run и пытается захватить его
kernel lock. Занятый lock — единственный признак активного run; наличие pending
`message` на решение не влияет.

Метаданные Codex session читает отдельный Python parser. Он поддерживает
legacy-сообщения `event_msg/user_message|agent_message` и текущие
`response_item/message` с `role=user|assistant`. Если JSONL содержит оба
представления, parser детерминированно выбирает legacy-формат целиком и не
смешивает события. При наличии только текущего формата соседние user messages
считаются одним логическим вводом с последними доступными timestamp и текстом:
так внедрённые `AGENTS.md` и `environment_context` не становятся preview вместо
первого запроса. Context берётся из последнего полностью пригодного
`event_msg/token_count`; неполный более новый snapshot не смешивается с полями
предыдущего. `token_count` с явно заданным `info: null` является штатным
событием без usage snapshot: он не сбрасывает найденный context и не создаёт
предупреждение. Отсутствующий `info`, неподдержанный тип или неполный объект
`info` считаются несовместимым форматом и дают одно предупреждение на событие.

Распознанное событие с отсутствующим или неподдержанным полем не отменяет
остальные метаданные session. Parser использует доступные поля и возвращает
отдельное детерминированное предупреждение с номером строки и указанием, когда
его поддержку нужно расширить. Такие предупреждения не делают run невалидным
и не мешают GC использовать найденные timestamps.

`orc pin <run_id>` атомарно создаёт marker `pinned`, а `orc unpin <run_id>`
удаляет его. Pin/unpin, purge и GC сериализуются отдельным maintenance lock. Во
время перемещения GC и purge удерживают run lock, поэтому resume того же
`run_id` не может с ними пересечься. Перемещение в trash удаляет run из
`orc list`, `orc resume` и разрешения `orc cd`, но не удаляет Codex session
logs. Arc worktrees обрабатываются отдельным этапом того же GC после runs.
До создания maintenance lock и любых изменений state root проверяется как
безопасный отдельный каталог: `ORCHESTRATOR_HOME` не может быть symlink,
filesystem root или effective home пользователя.
Marker `pinned` должен быть обычным файлом, а не symlink. Pin, list, purge и GC
отказываются работать с невалидным marker. `orc unpin` служит безопасным
recovery для symlink: удаляет только сам directory entry без следования target;
прочие non-regular marker остаются ошибкой.

`orc purge <run_id>` адресно выбирает один сохранённый run без применения
keep-last и retention. Под общим maintenance lock команда отказывает для
pinned run и при занятом run lock, сообщает причину и завершается с ненулевым
статусом. Успешный purge переносит run в orchestrator trash с текущим timestamp,
но не удаляет его навсегда, не очищает Codex session logs и не обрабатывает
остальной trash. Затем по правилам GC удаляется только содержащий рабочую папку
этого run prunable worktree, если его не защищает другой run; cleanup остальных
worktrees и окончательное удаление trash остаются обязанностью `orc gc`.
Если cleanup worktree завершается ошибкой уже после строки `Purged run ... to
trash.`, команда возвращает ненулевой статус без отката: run к этому моменту
уже находится в trash.

### Worktree status и ограничения `arc-wt`

Исследование ложных `status is not prunable` показало два независимых источника
устаревшего состояния в `arc-wt`:

- расчёт `prunable` опирается на локальное представление trunk, которое может
  отставать от remote trunk;
- расчёт использует сохранённое в state `arc-wt` имя source-ветки. После
  `arc submit` фактическая ветка checkout может стать `pr-*`, тогда как в state
  остаётся исходное имя вроде `PROMOPAGES-*`. HEAD уже может находиться в trunk,
  но `arc-wt` продолжает возвращать non-prunable по устаревшей ветке.

Поэтому state `arc-wt` остаётся источником mount inventory и быстрым штатным
источником status, но не единственным источником решения об удалении. GC сначала
получает inventory без status командой `ya tool arc-wt list --porcelain`, а
затем обрабатывает worktrees строго по одному. Такое разделение позволяет
восстановить конкретный `unmounted` worktree до проверки и не превращает
проблему одной записи в недостоверный общий status всех записей.

Для записи с маркером `unmounted` сначала выполняется точечный
`arc mount -m <worktree-path>`. Для `mount-shared` команда явно получает
сохранённый `-S <store>`, настроенный `--object-store <object-store>` и
`-r <repo>`, чтобы `arc` не выбирал последний store неявно. После remount
маркер `unmounted` обязан исчезнуть.

Перед точечным `ya tool arc-wt list --porcelain --status <name>` GC читает
фактическую ветку через `arc info --json`; сохранённое поле `branch` из state
`arc-wt` в решении не участвует. Перед status GC освежает представление о
remote trunk, а локальный trunk передвигает только там, где это не затронет
checkout:

- на фактической ветке `trunk` выполняется только `arc fetch trunk`, потому что
  он обновляет remote ref, тогда как `arc pull trunk` передвинул бы текущий HEAD
  и checkout;
- на любой другой фактической ветке выполняется `arc pull trunk`: он обновляет
  локальный trunk, не меняя текущий HEAD и файлы checkout.

Это различие сохраняет строгую семантику `--dry-run`: команда может обновить
служебные refs и prerequisite mounts, необходимые для достоверной оценки, но
не меняет текущий checkout даже при неконсистентном состоянии worktree.

Штатный `prunable` от `arc-wt` является быстрым положительным ответом. Если
`arc-wt` не вернул его и не сообщил `dirty`, GC использует независимый fallback:
подтверждает пустой `arc status --short`, затем запрашивает не более одного
коммита из `arcadia/trunk..HEAD`. Пустой диапазон означает, что в HEAD нет
коммитов вне remote trunk, и считается безопасным эквивалентом `prunable`.
Ограничение `-n 1` достаточно: для отказа от удаления нужен любой один
несмёрженный коммит, а полный список не нужен. Этот fallback выполняется только
после отрицательного ответа `arc-wt`; локальные замеры на worktrees с trunk,
выросшим на десятки тысяч коммитов, занимали около 0.20–0.27 секунды и были не
медленнее проверки через `merge-base` (около 0.29–0.38 секунды).

Ошибка inventory, remount, чтения фактической ветки, обновления trunk,
точечного status или независимой проверки останавливает GC на текущем
worktree: отсутствие достоверного ответа никогда не трактуется как разрешение
на удаление. После принятия решения GC завершает обработку текущей записи и
только затем переходит к следующей.

Worktree защищён, если внутри него находится working directory из `state`
любого оставшегося run. Из остальных записей GC исключает `trunk` и worktree с
маркером `here`, затем выбирает записи с маркером `prunable` или с подтверждённым
эквивалентным состоянием clean и `HEAD`, уже содержащимся в remote trunk.
`worktree-dir.txt`, pin и run lock напрямую в этом решении не участвуют: pinned
и активные runs остаются в `runs/`, поэтому их `state` обеспечивает ту же
защиту.

Выбранный worktree удаляется по точному имени через `ya tool arc-wt remove`
без `--force`. Внутри штатного пути `arc-wt` вызывает безопасный unmount с
`force=false` и `--forget`; печатаемая самим инструментом рекомендация
`diskutil unmount force` является только текстом ошибки и автоматически не
исполняется. GC перехватывает этот служебный вывод, чтобы нормальная занятость
mount не выглядела как авария с предложением опасной команды.

Если обычный unmount сообщает `Resource busy`, GC выводит одну короткую строку
с первым найденным PID, сохраняет worktree и продолжает обработку остальных.
Типичный держатель mount — оставленный shell, чья current working directory
находится внутри worktree. GC не завершает такой процесс и не выполняет
force-unmount. Для прочей ошибки полный вывод показывается только с `--verbose`,
после чего GC останавливается, не форсируя изменение.

В режиме `--dry-run` prerequisite remount размонтированных worktrees и
обновление trunk всё равно выполняются, но текущий HEAD и файлы checkout не
меняются, runs не перемещаются и worktrees не удаляются. Worktrees оцениваются
так, как будто runs с решением `Would collect` уже перемещены: это позволяет
одним запуском увидеть полный будущий результат.

Каждый запуск `orc gc`, в том числе при отсутствии сохранённых runs, навсегда
удаляет run directories, которые провели в orchestrator trash не менее 30 дней.
Параметр `--trash-retention <duration>` переопределяет этот срок и принимает
тот же формат duration, что `--retention`.
Момент перемещения фиксируется временем изменения trashed run directory и не
выводится из времени создания или последней активности run. `--dry-run`
показывает такие удаления, но не выполняет их. Удаление trashed run само по
себе удаляет только orchestrator metadata; Codex session logs не очищаются, а
worktrees независимо рассматриваются следующим этапом GC.

`SessionStart` hook только добавляет новую session activation с её временем и
идентификатором сессии; подготовительные процедуры к этому моменту уже
завершены orchestrator. Последняя activation определяет сессию, которую
orchestrator продолжает после перезапуска. Из переменных окружения Codex
получает только `ORCHESTRATOR_RUN_ID` и запускается с рабочей папкой из run
state.

Новый запуск, явный resume и продолжение после смены worktree используют одну
функцию и одну shell-команду запуска Codex. Различия new/resume представлены
только массивом аргументов. Каждый вариант получает `codex.system.prompt` из
корня harness через параметр `model_instructions_file`.

Orchestrator запоминает рабочую папку пользовательского shell при своём
запуске. Перед каждым запуском Codex он показывает run ID, рабочую папку,
корень harness и Pwd пользовательского shell. Если Codex запускается в другой
папке, вывод также предупреждает о неизменившейся папке shell. После выхода
те же поля и предупреждение показываются повторно вместе с командой resume. В
интерактивном терминале вывод использует ANSI-цвета; `NO_COLOR` отключает их.

## Персональные project overrides

Project overrides позволяют хранить персональные инструкции отдельно от
целевых проектов и применять их в основном checkout и worktrees. Внутри
единого pre-launch pipeline непосредственно перед каждым запуском Codex
orchestrator приводит инструкции в соответствие с источниками из
`project-overrides/<arc-relative-project-path>/`.

Материализованные в целевом проекте инструкции являются рабочими артефактами:
их нельзя добавлять в Arc, коммитить или передавать в submit. Изменять нужно
только источники в harness. Персональные overrides не изменяют командные
`aisuite/rules/`.

## Наблюдение за runs

Orchestrator предоставляет текущие данные Arc checkout и связанного run:
версию harness, время создания run, сохранённую рабочую папку, текущую сессию
и сессию, выбранную для продолжения. Вне активного run связь определяется
сначала по точному совпадению рабочей папки, затем по ближайшему сохранённому
родительскому каталогу.

По умолчанию список содержит только runs, чья сохранённая рабочая папка
находится внутри текущего Arc checkout. `orc list --all` показывает runs из
всех checkout. Обычный вывод заканчивается подсказкой про `--all`.

Список runs упорядочивается от новых к старым. Внутри run `orc list` показывает
уникальные сессии от новых к старым по времени их последней activation. Перед
чтением метаданных Codex и формированием вывода session activations
дедуплицируются по `session_id`: для каждой сессии выбирается marker с наиболее
поздним временем активации. Дедупликация применяется только к представлению
списка и не изменяет неизменяемую историю activations. Сессия с самой новой
activation помечается как выбранная для продолжения. Заголовок run содержит
идентификатор и время создания; условный маркер `pinned` при наличии
размещается между ними и отделяется `·` с обеих сторон. Следующие строки —
короткое имя Arc worktree и относительную папку внутри него с заголовками
`worktree` и `folder` в верхнеуровневом дереве. Под заголовком `sessions` для
каждой сессии выводятся сокращённые времена первого и последнего сообщения и
процент заполнения контекста, затем начало первого пользовательского сообщения.
Превью выводится отдельной следующей строкой, нормализуется в одну строку и
обрезается с многоточием по ширине текущего терминала. Статистика отражает
текущий снимок, а не исторический максимум. Если parser обнаружил частично
неподдержанный или неполный формат, `orc list` после preview выводит отдельную
строку `warning:`; пригодные времена, context и текст при этом сохраняются.

При прерывании `orc list` или `orc gc` через `Ctrl+C` orchestrator выводит одну
короткую строку `orc <command> interrupted.` в stderr и завершается с кодом
130. Stderr worker-процесса при таком прерывании отбрасывается, поэтому
traceback дочерних Python-процессов не попадает в терминал.

Рабочая папка разрешается по идентификатору run или по сохранённому имени
worktree. Разрешение пути не изменяет рабочую папку вызывающего процесса.

## Подготовка worktree

`tool-prepare-worktree.sh` запускается по абсолютному пути из каталога
обнаруженного workflow skill. Рабочая папка tool call остаётся рабочей папкой
вызывающего проекта; bundled-файлы runtime разрешаются относительно самого
entrypoint и не зависят от `PATH`.

Подготовка worktree последовательно обновляет trunk в настроенном main Arc
checkout, создаёт или находит worktree, переключает run state и создаёт
уведомление о перезапуске. Git indicator создаётся позже единым pre-launch
pipeline. Ошибка любого шага до уведомления завершает pipeline без команды
перезапуска.

Имя workflow worktree детерминировано и не содержит timestamp: при наличии
тикета используется `<TICKET>_<short-description-slug>`, без тикета — только
`<short-description-slug>`. Повторная подготовка с тем же именем использует
уже существующий worktree.

Абсолютный путь подготовленного worktree сохраняется отдельно для последующего
разрешения по имени. Переключение run state изменяет только рабочую папку;
история session activations остаётся отдельной.

Уведомление атомарно записывает `restart-agent` и не завершает Codex
автоматически. После добровольного завершения сессии orchestrator удаляет
уведомление, выбирает последнюю session activation и продолжает её в
сохранённом worktree. Завершение без уведомления завершает orchestrator.

Для statusline строго в корне Arc worktree создаётся отдельный пустой
Git-репозиторий. Рабочая папка run используется только для разрешения корня
checkout и не содержит Git indicator. Ветка indicator получает короткое имя
задачи, а существующий `.gitignore` Arcadia не изменяется. Pre-launch проверяет
indicator перед каждым new, resume и restart, сохраняя существующее имя ветки.
Для созданного workflow worktree короткое имя задачи выводится из имени
checkout; для остальных запусков используется полное имя корня Arc checkout.
